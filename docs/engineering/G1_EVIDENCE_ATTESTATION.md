# Independently signed evidence custody checkpoints

Migration 0024 adds an installation-wide dedicated NOINHERIT evidence auditor login. It can call only attestation_inventory; no direct table, ciphertext, key, upload or download privileges. A read-only repeatable-read transaction returns up to 4096 sorted evidence UUIDs, SHA-256 custody commitments, and a database-encrypted flag. The commitment covers immutable evidence identity/scope/hash/creator/time, hashed storage reference and, for encrypted objects, the session/request, media type, size, key version, scan policy, ciphertext commitment and creation time. The database independently recalculates ciphertext SHA-256 and rejects inconsistent associations. Legacy evidence commitments attest metadata only, not external file bytes. No proof of scanner efficacy, author identity outside local records, or completed download. Access events are deliberately not part of this immutable object checkpoint. The signer does not decrypt or validate plaintext; recovery and authorized retrieval provide separate AEAD integrity gates.

Use createEvidenceAuditor with a dedicated verified TLS pool and pinned login. Export only this snapshot to a separate trusted signing environment. signEvidenceCheckpoint requires a distinct Ed25519 key, explicit initial=true for genesis, or a previously signed manifest and independently trusted sequence/digest for successors. Persist each manifest/signature plus latest sequence/digest outside the database, preferably in an independently controlled immutable repository. verifyEvidenceCheckpoint requires the independent anchor; verifyEvidenceTransition requires consecutive sequence, exact previous hash and unchanged prior records; compareEvidenceInventory reports new unattested records and rejects omissions or changes. Signed manifest metadata is pseudonymous and should remain private. No automatic checkpoint publication, trusted timestamp authority or real offsite anchor configured. Never accept a digest supplied only alongside the untrusted manifest; verifier must obtain the expected latest checkpoint separately. Operator must prevent parallel forks via exclusive signing/change control. Key rollover requires an independently approved new trust anchor; do not reset genesis to conceal history. This protects against alteration of previously anchored history, not fraudulent original input or a malicious signer/DBA colluding before attestation. Independent production operational validation and external custody remain buyer deployment prerequisites. CI uses synthetic keys and real PostgreSQL, not a commercial signing provider.
