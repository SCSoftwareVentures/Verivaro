# Secure evidence ingestion (initial narrow file policy)

Optional runtime configuration: add ingestion {keyId,keyFile,scannerSocket} and logins.ingestion {user,passwordFile}; keyFile is owner-only canonical 32-byte base64url, distinct from existing keys, scannerSocket is absolute trusted clamd Unix socket. With no ingestion config the endpoint is disabled. Use a dedicated NOINHERIT login for verivaro_evidence_ingestor, separate from runtime; no table access. The only upload endpoint is POST /api/v1/tenants/:tenant/projects/:project/evidence with exact Origin, opaque browser cookie, text/plain; charset=utf-8, fixed Content-Length 1–262144 bytes, UUIDv4 Idempotency-Key and lowercase SHA-256 X-Evidence-SHA256. No arbitrary filenames, paths, archives, images, PDFs or binary formats. Strict UTF-8 and bounded control-character checking is not content sanitization; treat evidence as untrusted and never render it as HTML. Content type and size are engineering defaults. Malicious content found, malformed text, mismatched hash or scanner failure never creates an evidence row. Preflight and final commit check current signed scope and contribution permissions; revocation during scan denies the commit. The dedicated ingestion process and independently managed scanner are trusted boundaries, not an independently signed scan attestation. Scanner adapter uses bounded clamd INSTREAM over a local Unix socket; only exact OK accepted, fail closed on errors/timeouts. Configure fresh definitions, malware-engine hardening, scanner isolation and socket ownership/permissions. Synthetic protocol tests are not a real antivirus efficacy test.

Incoming bytes are held in bounded memory (four in-flight uploads); the quarantined object is encrypted before scan and only clean objects committed. Rejected files are discarded, not retained in a persistent malware quarantine. No plaintext file is written. AES-256-GCM envelope binds tenant, project, object ID, SHA-256, size and key version; database stores ciphertext and an immutable evidence-object chain of custody record with actor/session/request ID and scan policy. Atomic evidence row and encrypted object; exact retry returns one original ID; conflict rejects different content under same actor/request ID. Global 4096 database-backed objects cap; each <=256 KiB (roughly 1 GiB max logical payload), no quotas per tenant yet. Keep independent key custody and previous version keys; recovery requires all relevant keys. This implementation stores encrypted objects inside PostgreSQL and does not expose a download endpoint for them. Existing release/share path is for externally released export objects; no automatic release.

For recovery use createEvidenceRecoverySource({client,sourceRoot,readKey}) as objectSource for createEvidenceBackup, on the same quiesced database snapshot. It decrypts/validates database-backed objects and streams them to encrypted backup; legacy UUID files still require their private source. A missing/mismatched encrypted object fails closed, never falls back silently. Original inventory/receipt includes all evidence, including database-backed evidence; full recovery tests compare source/restored ciphertext rows and check decrypted content. Independent key backup and dense data recovery capacity need operational validation. Prior 8 GiB evidence limit remains for aggregate backups, not individual uploads. No production scanner, external services or live deployment; CI fixtures use a simulated clamd protocol and real database/HTTPS. Further priorities: supported binary formats, actual malware engine gate, upload quota governance, authorized evidence retrieval/preview, tamper-evident independent attestation.

## Successor migrations 0022–0023

Adds strict PNG (8-bit RGB/RGBA, no ancillary chunks, up to 1 megapixel, validated CRC and bounded inflation) and a canonical single-page ASCII-text PDF format only. General PDFs, JPG and typical camera PNGs with extra metadata may be rejected. Both new formats remain 256 KiB compressed maximum. Per tenant 256 objects/32 MiB and per actor per tenant 8 MiB, all enforced atomically with the original global count limit; 507 means quota exhausted. Exact retries do not consume quota again. Separate evidenceReader login when ingestion enabled, attachment-only GET /api/v1/tenants/:tenant/projects/:project/evidence/:evidence/download with current membership, session check, full AEAD and plaintext hash verification before sending, no ranges or inline preview. Access event attests authorized ciphertext retrieval, not completed download. Config ingestion.retiredKeys optionally lists up to 15 {keyId,keyFile}; previous keys read-only, newly written objects use active key, do not retire keys still referenced. No automatic key deletion or re-encryption. All keys need external escrow; access records are not yet independently anchored. No general PDF sanitation claim.
