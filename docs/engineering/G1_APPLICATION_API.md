# Read-only application API and distributed admission

The initial application API exposes three fixed GET routes: /api/v1/tenants/:tenant/projects, /api/v1/tenants/:tenant/projects/:project, and /api/v1/tenants/:tenant/projects/:project/evidence. No query strings, request bodies, arbitrary operations, SQL, encoded aliases, cross-origin credential use or bearer-token bypass. Exact configured Host and origin; no CORS. Duplicate sensitive header/framing fields rejected, only opaque browser session resolver is used, local JWT independently verified, and actual database operation still protected by signed context and live RLS. Unauthorized tenant/project lookup is indistinguishable from missing resource; empty evidence result does not disclose project existence. Database failures return generic 503. Public response projection excludes storage paths and actor identifiers; names projected to 256 characters, lists capped at 200 and serialized response at 512 KiB. Pagination and write endpoints not implemented.

Separate dedicated PostgreSQL admission role and two fixed functions implement transaction-serialized minute buckets, default global 600 requests/minute, peer 120, actor 60, across replicas sharing the same DB and HMAC key. Global budget charged before session lookup, actor budget after token verification. No raw address or actor ID stored, IPv4-mapped addresses normalized, IPv6 aggregated /64, forwarded headers ignored. Fixed-window bursts, shared proxy/NAT limits and distributed attack limits remain; rate enforcement is fail-closed on DB errors, no per-tenant fairness, quotas are engineering defaults, not measured production capacity. Local in-flight cap 16, upstream server/proxy must enforce TLS, headers/timeouts/connections and edge flood controls. Recovery resets transient counters. Live CI uses two real HTTP replicas, real separate database logins and real JWT+RLS, with a synthetic session resolver; existing browser integration separately validates the actual cookie/session resolver. No deployment or external network testing. Future priority: wire the browser handler and API together in a deployable hardened runtime, add paging, mutation-specific CSRF/idempotency and audit telemetry before exposing write functionality.
