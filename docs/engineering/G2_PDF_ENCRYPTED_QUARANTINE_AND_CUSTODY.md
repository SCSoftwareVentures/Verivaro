# Original PDF quarantine and signed derivative custody statement

A **separate offline, operator-only** original-PDF vault stores an otherwise unsupported original PDF as an AES-256-GCM encrypted envelope. Prior to sealing, a required injected local antivirus scanner must return *exactly* `clean`; infected, unavailable, cancelled, or content-modifying scans fail closed. The caller must provide a tenant ID, project ID and a trusted absolute quarantine root owned by the process with mode 0700. The vault allocates a new UUID filename and writes only encrypted bytes using O_EXCL, O_NOFOLLOW, 0600 and synchronous file writes. On read it checks owner, mode, size, AES-GCM authentication, exact scope-bound associated data and original SHA-256; an incorrect key, scope, hash or modified file is rejected. The original is **not** accepted as a normal Verivaro evidence object and is never exposed through the existing upload route.

Separately, an **Ed25519 signed custody statement** must re-read the original from quarantine, independently verify the canonical derivative, and bind the tenant, project, quarantine identifier, conversion identifier, original and derivative SHA/length, page-specific raster digests, signing-key fingerprint and timestamp. Verification requires an *independently trusted public key* and can optionally rehash the original and derivative. The signature proves the signer examined matching bytes and stated this linkage at issuance time. It is **not** independent timestamping, legal notarisation, evidence authenticity, proof of faithful rendering, or guaranteed future retention. No raw source bytes, original filenames or personal details are embedded in the receipt. The original and receipt still need independent encrypted backup, retention/deletion procedures, and administrative access controls.

**Operational safety**: no API routes, web handlers, database roles or production integrations are modified. The quarantine directory and Ed25519 private key are operator-provisioned and physically separated from the untrusted PDF worker. Signature issuance is deliberately separate from untrusted PDF rendering. An antivirus engine connection, OS-verified isolation, durable audit/backup chain, and privacy/legal retention review are prerequisites to any live use. CI synthetic fixtures test tampering, wrong keys, rejected scans, scope separation, encrypted storage, and signature checks. No customer files processed, no additional expenditure, no deployment. CI pending.

If the secure write fails or cancellation is detected before completion, the vault attempts to remove the newly created quarantine object rather than leaving an unreferenced original. Storage failures during cleanup still require an operator to reconcile orphaned files; the module cannot guarantee deletion after a power loss. No automatic retention/deletion schedule is asserted.

The actual ClamAV CI gate now includes a second integration test through the quarantine module: a clean canonical PDF is stored encrypted and subsequently re-read; a PDF containing a harmless locally defined ClamAV signature is rejected before any new vault file is created. The signature is test data, not live malware. This verifies the scanner verdict adapter, not the full production quarantine environment.
