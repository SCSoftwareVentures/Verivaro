# Recipient-bound sharing (G1)

Candidate gate: explicit recipient UUID, known through an active registered identity session when the owner grants access. The public bearer route never resolves recipient-bound grants; sensitive exports can use only the recipient route. The separate gateway verifies an RS256 local identity JWT with a configured issuer and dedicated recipient audience, and sends verified actor, session and expiry to the restricted database resolver. It checks live session, actor and issuer generations, expiry, export and grant revocation twice, including after integrity verification. Recipients do not need project membership. A recipient account disable permanently invalidates its historical links, even following recovery. A revoked session denies that session; a fresh authorized session for the same actor may access an otherwise valid grant. An authenticated recipient can receive another share only if explicitly authorized.

The dedicated gateway is trusted to verify JWTs (database receives verified claims, not raw JWT). Separate credentials and audience provisioning are mandatory. POST /public/share/recipient-download uses Authorization: Bearer <share-token> and X-Verivaro-Recipient: <identity-JWT>; neither may be logged. No actual IdP, recipient invitation/identity directory UI, MFA enforcement, protected cloud storage or distributed rate limits are implemented. Explicit recipient selection and consent remain product work. File limit remains 8 MiB default; revocation cannot recall delivered data or remove the final-check/transmission race. No production data or deployment.
