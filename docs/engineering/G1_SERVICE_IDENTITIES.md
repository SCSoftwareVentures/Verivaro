# Service identity and connection isolation

All five application database adapters now share a fixed role/login guard. Each checkout discards old session state, forces pg_catalog search path, rejects elevated or inherited login/group attributes, extraneous direct or transitive memberships, ADMIN OPTION, database CREATE and schema CREATE. A distinct dedicated login must have only intended group membership (NOLOGIN group) and no direct application table/column/function/schema access. Configured expectedLogin pins the exact login and disallows using the group as a login; provision distinct nonprivileged NOINHERIT login per service/replica and set expectedLogin in every production adapter. Legacy CI group-as-login fixtures remain supported only when no expectedLogin is supplied; production launcher always pins it. This is a guard against misconfiguration, not defense against a malicious DBA, compromised host, or a race after privilege checking.

Monitor worker, reader and alert launcher now requires private owner-only password file VV_DB_PASSWORD_FILE, explicit PGHOST/PGUSER/PGDATABASE, and an independent PEM CA file VV_DB_CA_FILE for TLS with certificate verification and DNS hostname. No environment PGPASSWORD, PGOPTIONS, connection-string or TLS override. Explicit VV_ALLOW_LOCAL_PLAINTEXT=1 is reserved for literal loopback isolated tests. Use distinct credentials, restrictive file ownership and trusted path ancestors; restart processes on credential rotation and revoke/terminate old logins explicitly. TLS wiring is implemented; production PKI, actual remote TLS connection and certificate rotation are not tested by this gate. Password strings necessarily exist in process memory; file-based delivery is not a vault. No live service deployed. PostgreSQL grants, database/schema ACLs and external provisioning still require independent review. Real CI tests grant and revoke synthetic adverse permissions and check denial before admission operations.
