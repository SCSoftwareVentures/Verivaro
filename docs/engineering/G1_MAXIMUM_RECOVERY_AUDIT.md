# G1 maximum recovery validation and security regression

The separate CI capacity workflow exercises a full 2 GiB encrypted logical byte stream and a full 8 GiB evidence bundle (16 x 512 MiB), with bounded-memory roundtrip, exact digest validation, cleanup and RSS ceilings. The evidence fixtures use sparse source files with unique nonzero markers and optional sparse zero-block restore. Ciphertext is written in full; all logical restored bytes are read and hashed. These synthetic storage benchmarks do not measure real PostgreSQL data loading, network, multi-user performance or production RTO. A physically dense destination needs capacity for all output bytes; sparse mode is opt-in and must not be used as a quota guarantee.

Add advisory filesystem headroom checks before backup archive creation and authenticated recovery staging, and before dense evidence output. ENOSPC still fails closed; external writers can race statfs. A dedicated quota, separate recovery cluster and trusted storage remain mandatory. Database creation now starts with ALLOW_CONNECTIONS false; PUBLIC CONNECT is revoked before enabling connections; ordinary-login privilege checks occur both before and after pg_restore. Privileged administrator access remains trusted.

Full post-migration and restored-schema audit checks service role attributes, indirect elevated role memberships, schema creation permissions, direct table privileges, forced RLS, SECURITY DEFINER search paths/public EXECUTE and cross-service function allowlist. The audit is an internal regression, not an independent penetration test or certification. Remaining risks: production role provisioning and indirect privileges of actual service LOGIN principals, future function overloads, upstream identity provider, storage provider, TLS/egress controls, external key custody, reviewer identity governance, actual network abuse resistance and legal review. No real data or paid infrastructure used.
