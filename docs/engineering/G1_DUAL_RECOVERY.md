# G1 independently approved emergency recovery

The old caller-supplied UUID-only authorization is replaced by a registered request tied to one specific lockdown. The recovery executor can request and execute, but cannot approve. Two distinct active operator identities must approve via independently provisioned database login principals; the affected account cannot approve its own recovery. Requests expire after 15 minutes. Requests, approvals, and identity transition history are append-only. Execution verifies current lockdown, approval count, operator status, expiry, and one-time use, then atomically invalidates previous sessions and sets the existing authentication fence.

Provision separate logins for each approver, map each to an independently verified person, restrict role memberships and require upstream MFA and approval evidence. The database enforces distinct mapped principals; it cannot establish that real people are independent without correct provisioning. Operator registry changes are privileged administrative actions, not ordinary service functions. Approval validity is checked against operator status at execution; re-enabling a disabled operator can make their unexpired approval eligible again, so incident handling must invalidate pending requests via a fresh lockdown or expiry. No real identity-provider integration or production approval workflow is claimed. The CI migration-sequence gate first validates migration 0006, then applies 0007 and verifies the tightened authorization. A full post-upgrade regression replay is an additional release task.
