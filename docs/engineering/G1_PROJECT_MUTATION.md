# G1 project rename mutation

PATCH /api/v1/tenants/:tenant/projects/:project accepts only application/json with exactly name and revision, a canonical UUIDv4 Idempotency-Key header, and the exact application Origin. Maximum 2048-byte fixed-length body and three-second read deadline, no chunking, compression, duplicate keys/headers or alternate endpoint. Name 1–128 Unicode code points, max 512 UTF-8 bytes, trimmed and no control/lone surrogate characters. Response includes revision. Same-origin cookie authentication and existing peer/actor limits apply.

The database checks signed transaction context and current active session, requires both tenant and project owner and locks lifecycle, membership and project rows. Revision must match current value for a new request; exact retry yields original result even after later changes, but requires current permission. Reused idempotency key with different payload/project or stale revision returns 409; unauthorized returns uniform 404. Atomic update, receipt and immutable audit row, with prior/new name digests, actor, session, revision and request ID. Raw names are not copied to the audit. SHA-256 is not anonymization. No direct runtime UPDATE or INSERT: previous evidence INSERT capability is withdrawn until verified evidence ingestion is implemented. No generic SQL or client supplied actor. The audit is protected from service writes and ordinary modification/truncation, not a cryptographically independently anchored log or malicious administrator proof. No automatic deletion; retention/legal hold and storage growth require explicit governance. Backup gates compare receipts and audit rows with restored contents. Historical pre-0020 fixtures retain read compatibility via revision fallback; the deployed runtime requires latest migration for writes. Synthetic CI verifies concurrency, role intersection, rejection, audit immutability, and real authenticated HTTPS write. Project rename is the only new write operation, not all domain CRUD. No deployment.
