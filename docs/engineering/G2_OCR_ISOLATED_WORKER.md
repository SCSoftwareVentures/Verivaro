# OCR worker security boundary

Linux deployment reference uses a dedicated non-root `verivaro-ocr` account, shared `verivaro-ocr-client` group, systemd credential delivery, restrictive socket directory, AF_UNIX-only private network, hard memory/CPU/task/file-descriptor limits, no core dumps, read-only system and isolated temporary directory. Install the checkout read-only at `/opt/verivaro`, install Node 22 and the trusted distro Tesseract English data, provision a random 32-byte raw credential as root (worker systemd LoadCredential), and provision a separate app-owner-only copy of the same key. Only the application principal should be in the socket group. Do not run the worker as root or share other application credentials. The application is not wired to this worker yet; production installation and enforcement need validation on a compatible Linux system. The service never stores images or logs OCR contents. Protocol uses fresh independent 256-bit client and server challenges, a worker HMAC proof verified before the app sends original image bytes, and length-bounded HMAC-SHA-256 request and response frames bound to both challenges using separate domain labels. The local socket is not encrypted; OS isolation and restrictive path permissions remain necessary. Caller receives verified response integrity, not correctness of transcription. One active OCR recognition, four sockets, bounded timeout and cancellation; unknown, unauthenticated and malformed requests fail closed. Unit probes use real local Unix sockets and CI actual-engine fixture now passes through transport. No cloud service or paid dependency. Existing OCR preview remains unverified and read-only. No production deployment. CI pending.
