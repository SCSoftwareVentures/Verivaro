# Project administration and recipient workspace

Migrations 0027–0028 add owner-scoped project creation, project membership directory, access assignment/revocation and scoped recipient share management. Creation auto-assigns only the authenticated creating tenant owner as project owner. Changes require both tenant and project owner; target must already be a current non-owner tenant member, not disabled, and an existing project owner cannot be changed. Viewer or exact tenant role only, no elevation; assignments expire after 30 days. No tenant enrollment, owner transfer, account creation or deletion. Change requests carry the prior membership generation (null for new) and UUID request ID. Atomic replay receipt and append-only audit record, stale generation conflict, rotation of share/approval generations. Caps: 200 projects per tenant, 200 memberships per project, 32768 administration events globally. Owner directory limited to 200 active tenant-member records; no external identity directory. A revoked tenant member already loses access independently. Existing administrative workflows remain necessary for owner succession and tenant membership management.

Recipient sharing is restricted to approved, current released evidence, existing active recipient identity/session, exact tenant/project owner, recipient code 32 random bytes, 15-minute expiry and max 32 historical shares per export. Client-generated code is passed in bounded same-origin POST and only its hash stored; retry uses same code and share UUID. No automatic messaging or public URL credential. The owner sees code once in the UI and must convey privately; recipient signs into the workspace and submits code via header. No caller-provided JWT accepted. Runtime projects a trusted internal recipient request to existing gateway; it rechecks authorization after full hash verification. Revocation/expiry blocks future transfers. Current new browser runtime requires logins.recipient when release enabled. Older raw issuance/revocation SQL grants are withdrawn; legacy standalone tests run before successor migration. No real provider accounts or delivery testing; actual browser rendering still requires separate testing. Local code state is in memory only, not persisted; ambiguous issuance must be reconciled via share list. Release source must remain on encrypted private volume. No full CRUD, archive lifecycle, tenant admin or production capacity claims.
