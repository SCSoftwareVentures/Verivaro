# Project privacy controls — engineering increment
Migration 022 adds a bounded repeatable-read project records export, explicit field redaction of storage keys and share-token hashes, audit digest, and separate owner-only endpoints. Caller must be both active tenant owner and project owner. It is not a full tenant export: other projects, original bytes, identity subjects, private audit/worker records are excluded; request authorised operator handling. Existing verified original download is separate. Oversized exports fail closed rather than truncate or silently omit sections. Export is delivered as sensitive JSON, never published. Retention revisions record an owner-selected period and legal hold with rationale; dates are not statutory advice or a deletion scheduler. Erasure request requires an explicit current policy, independent second active tenant/project owner, unchanged graph generation and no recorded hold. Approval revokes existing external shares and prevents new ones until cancellation. Neither request nor approval deletes bytes or records, and internal access remains; no erasure completion state is exposed. A hold/policy change after approval requires operator re-evaluation, and cancellation does not restore old grants. All changes are historical; runtime has no table write or delete authority.
Before actual erasure: independent legal approval and retention/hold checks; authenticate subject, establish scope, reconcile active writes/jobs, freeze internal access and revoke shares, inventory original objects, derived text, caches, exports, logs, backups and processors; preserve only lawfully required minimal evidence; approve and run a separately audited operator procedure; verify deletion and replay a durable deletion ledger on restore. No such production operator execution or backup erasure is implemented here. Do not claim Australian Privacy Act/APP compliance or completed data deletion. APP 11 security/retention and access/correction requirements require qualified applicability review; no current legal verification performed. CI pending.

## Offline erasure and restoration increment
Migration 023 isolates exact project erasure behind a new ungranted operator role. No HTTP delete route and no production execution. Revalidate dual approval/current policy, authority, generation, reviewed table inventory, lease state, unique exact object scope and an explicitly approved plan digest. A quiesced operator writes a signed ledger outside the database and object root, fsyncs it, then commits scoped relational removal and a minimal independent tombstone. Only afterwards unlink exact previously inventoried private objects; retries reconcile from the durable signed ledger. Cross-tenant rows and tenant identities are deliberately retained. Restore gate requires an independently trusted complete ledger digest list and external verification key; missing tombstones or resurrected objects block cutover. It does not automatically destroy older backup copies or replay missing tombstones; those require a separately approved restore procedure. No forensic disk erasure, backup destruction, external processors, full tenant archive, private audit portability or legal compliance certified. Tenant inventory identifies other projects and explicitly marks inaccessible projects, with separate per-project export authorization. Production operator provisioning, service quiescence, durable external ledger storage and restore integration are buyer gates; synthetic integration exercises scoped deletion and stale-object denial. CI pending.
