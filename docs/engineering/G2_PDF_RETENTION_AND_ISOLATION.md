# Original-PDF retention and Linux isolation gate

The operator-only retention gate defaults to deny. A separate Ed25519 policy-signing key must sign the exact tenant, project, original PDF SHA-256, quarantine ID, policy revision and retention deadline. Two distinct, pre-registered operator signing keys must countersign the exact scope and policy; approvals expire in at most 48 hours. An injected authoritative live legal-hold registry must explicitly answer **false** at deletion time. Missing status, active hold, expired approval, early deletion, missing or reused signature, policy scope mismatch and cancellation all deny the operation. No legal retention period is hardcoded or selected by the app.

Quarantine exposes `destroy` **only when the trusted retentionGate is explicitly installed**; existing vaults are unchanged. After approval, it checks source file permissions/identity, writes and fsyncs a deletion-intent record containing an authorization hash, fsyncs the directory, checks inode identity, unlinks the encrypted object, fsyncs and atomically renames the intent to a tombstone receipt. Reads refuse in-progress deletion. Crash interruptions, orphaned intents, unsigned receipts, external legal-hold concurrency, immutable backup retention and physical media erasure require independent operational handling. Deletion is **not** connected to any public API, scheduler or production data.

The service profile has CI assertions and a systemd-analyze syntax verification step. This is a **static** configuration test, not proof of production Linux namespace/seccomp/cgroup isolation. Production requires host-level enforced-denial tests, credential isolation, actual resource exhaustion and hold-registry locking before deployment. Test deletions are only synthetic, temporary CI fixtures. No customer files, production actions, paid infrastructure or merge.
