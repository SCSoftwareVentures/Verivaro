# Expanded backup capacity and key lifecycle

The logical archive hard cap is 2 GiB; the existing 512 MiB default remains explicit. Set VV_BACKUP_MAX_BYTES to raise it for backup AND restore. Recovery-only encrypted staging accepts up to 2 GiB while public download limits, per-object caps and distributed download budgets remain unchanged. Evidence bundle aggregate cap rises from 2 to 8 GiB (4096 entries, 512 MiB per object). Provide dedicated disk quota and enough space for archive, staging and output; no production throughput or 8 GiB saturation guarantee. CI exercises actual 1 GiB encrypted streaming roundtrip with process-wide RSS ceiling, not a maximum-size real PostgreSQL restore.

Version 2 manifests authenticate an explicit key ID; a bounded keyring supports one active write key and previous read-only keys. Version 1 legacy archives require an explicitly configured legacy key; version 2 cannot be opened through the unversioned interface. Rotation chooses new keys for newly created backups without changing existing archive IDs or invalidating signed evidence catalogues. Never remove a retired key until all protected recovery copies have expired or been securely migrated and successfully restored. No in-place re-encryption of historic archives. The CLI accepts either VV_BACKUP_KEY or a private 0600 VV_BACKUP_KEYRING_FILE (not both); JSON shape: activeId, keys array of id/key objects with canonical 32-byte base64url keys, optional legacyKey. Store separately from backups with independent key custody, restrict trusted directory ancestors, and never commit keyring files. External KMS/escrow/rotation scheduling are deployment requirements.
